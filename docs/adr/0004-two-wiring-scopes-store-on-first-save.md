# Two wiring scopes, global by default; the store is created on the first save

> Superseded in part by [ADR 0005](0005-home-store-by-default-local-store-on-purpose.md): the first save creates the home store, the hook speaks in every directory, and `enable --project` creates no store.

> Amended 2026-10-29: each scope's wiring holds the per-prompt hook's UserPromptSubmit entry too (last consequence).

> Amended 2026-11-02: with no store yet, listing and searching find no memories instead of refusing (third consequence).

An agent is wired to mdmem in one of two scopes. In the global scope, the default of `mdmem enable`, the wiring lives in the agent's user-wide files and applies in every repository on the machine: the session-start hook speaks in every git repository, store or not, and the first memory write creates the store at the repository root. In the project scope (`mdmem enable --project`), the wiring lives in files committed with one repository, as 0.3.0's predecessor did for every project, and applies only there; enable creates the store if it is missing. A repository may be wired in both scopes, by different people: exactly one hook speaks, and the agent runs one mdmem server.

We chose this over keeping project files as the only wiring, which made every new repository need `mdmem init` and `mdmem enable` by hand before any agent remembered anything, and over global wiring alone, which would have left a team no way to wire a repository with a commit. A repository root is the only boundary the global hook trusts: outside git, `locateStore` walks up to the home directory for an existing store and would otherwise create one in the working directory, so a save in `~/dev` would make a store that every later `git init` under it stops seeing. Outside git the hook therefore speaks only where a store already exists, and a write creates one in the working directory.

## Considered options

- Claude Code's own model, a store wherever a session runs: rejected for the walk-up trap above.
- A per-repository opt-out (a marker file, a variable): left out; a `.memory/` appears only on a save, and a global gitignore hides it everywhere at once.
- Importing Claude Code's memories inside `enable`, as before: impossible once enable runs once per machine. The import now runs when a store is created, by whichever path creates it, for a repository where Claude Code is wired in either scope and the per-repository marker is absent; a new store has nothing to conflict with, so `--prefer` is gone, and an existing store gets no import.

## Evidence

- All three agents spawn a user-scope stdio server in the session's working directory (the launch directory, or the `-C`/`-w` directory), never the home directory or `/`, so the server keeps resolving the store from `process.cwd()`, walking up to the repository (Claude Code 2.1.306, Codex 0.160.0, IBM Bob 2.0.6, tested 2026-10-21).
- Claude Code runs exactly one server named `mdmem` when the user scope and a project's `.mcp.json` both declare one: the user-scope one until the folder is trusted and the project server approved, then the project one. An approval written to `.claude/settings.local.json` has no effect in an untrusted folder (tested 2026-10-22). Both definitions run `mdmem mcp`, so which one wins does not matter.
- User-wide files: Claude Code's hooks, `permissions.allow` and `autoMemoryEnabled` in `~/.claude/settings.json` and its servers at the top-level `mcpServers` of `$CLAUDE_CONFIG_DIR/.claude.json`; Bob's `~/.bob/settings/settings.json` (hooks) and `~/.bob/settings/mcp.json` (what `bob mcp add -s global` writes); Codex's `~/.codex/hooks.json` and `[mcp_servers.*]` in `~/.codex/config.toml`. Codex's hooks are stable and on by default, with no feature flag to set.
- Codex 0.164.0 (tested 2026-10-26 with a temporary `HOME` and `CODEX_HOME` and a model provider that cannot connect): in a trusted repository it lists the project's `.codex/hooks.json` beside `$CODEX_HOME/hooks.json`, and once both hooks are trusted, `codex exec` runs both SessionStart hooks, from the root, from a subdirectory, and from a linked worktree, whose project hook comes from the main checkout's `.codex/hooks.json` under that file's trust key. Codex's `hooks/list` for a linked worktree lists the main checkout's file only when the worktree's own folder has a `.codex/` directory: a worktree checked out from a commit before the wiring gets the global hook alone, and a worktree whose commit has `.codex/hooks.json` gets no project hook while the main checkout's has none (listed, not run, on 0.164.0 the same day). The trust was written with the app-server calls the TUI's review makes (`hooks/list`, then `config/batchWrite` of `hooks.state.<key>.trusted_hash`), not through the interactive prompt. With `[mcp_servers.mdmem]` in both the user config and the project's, Codex starts one server, the project's (`codex mcp list` agrees); both run `mdmem mcp`, so which one wins does not matter. Not verified: the interactive review prompt itself, and a `project_root_markers` other than Codex's default `.git`, which mdmem's walk to the work tree's root assumes.
- Claude Code records a folder's trust in its user config, `$CLAUDE_CONFIG_DIR/.claude.json` (else `~/.claude.json`), as `projects[<path>].hasTrustDialogAccepted: true` (verified 2026-10-22). Claude Code 2.1.310 (read from its bundle and its config on 2026-10-26) counts a folder as trusted when that key is set for the resolved path of any folder from the launch folder up to its work tree's root (up to `/` outside git), or for the main checkout's root, under which it records the trust of a linked worktree: none of this repository's linked worktrees had a key of its own, while its main checkout's was trusted. Its documentation says `claude -p` runs a project's hooks in a folder never trusted.

## Consequences

- Global scope sets `autoMemoryEnabled: false` in Claude Code's user settings, so its auto memory is off on the whole machine; project scope sets it in the repository's `.claude/settings.json` only. A project's `true` overrides a user's `false`, and the check keeps reporting it.
- The global hook entries carry a marker (`mdmem hook <agent> <part> --global`); the project entries stay as 0.2.0 wrote them, so a 0.2.0 repository is a project-scoped one with no migration. A global instance stays silent where the project's own hook entries are present (the server registration alone does not count). Codex follows the same rule, with the files it reads (amended 2026-10-26, below).
- In a repository with no store, the index part says the store does not exist yet and that the first `memory_write` creates it. Any memory write creates it (MCP `memory_write`, CLI `mdmem add`), with `MEMORY.md`. Until then, listing and searching (`memory_list`, `memory_search`, `mdmem list`, `mdmem search`) find no memories, their store line saying the first write creates it, and create nothing; a project with no store has no memories, and an agent shows a refusal as a failed tool call (amended 2026-11-02). Reading, editing or deleting a document refuses and says so. The creating write reports the store's path, the import's lines when it imported, and the existing note when git does not ignore `.memory/`.
- `mdmem status` reports each agent in both scopes and works without a store and outside any repository; the check reports the wiring alone there. A repository wired in both scopes is two status lines, not a problem. `mdmem disable` mirrors enable: global by default, `--project` for the repository's files; `--global` is gone.
- In an untrusted folder wired in both scopes for Claude Code, the global hook speaks (amended 2026-10-26; until then nothing spoke there before the folder was trusted, as in 0.2.0): it defers to the project's entry only where Claude Code's user config records the folder as trusted, by the rule in Evidence, so such a folder gets each part once, from the global hook, which says on stderr that the project's hooks wait for trust. A user config that is missing or cannot be read records no trust, so the global hook speaks, since a duplicate block costs less than a session with no memory (ADR 0002). We accept one gap: `claude -p` runs the project's hooks in an untrusted folder, where the global hook speaks too, so a headless session there gets each part twice; such sessions are rare, and the cost is one duplicate block. Bob's trust store is unknown, so its global hook keeps deferring, and an untrusted folder wired in both scopes for Bob gets nothing until it is trusted; `mdmem status` notes that Bob runs workspace hooks only in a trusted folder.
- `mdmem status` and the check note each agent wired in both scopes (amended 2026-10-26): a note, not a problem, saying that where its project hooks run its global ones stay silent.
- Worktrees are unchanged from ADR 0003: the store is keyed by the repository, so every worktree shares it. In project scope the wiring files travel with the commit, so a worktree checked out before that commit is not wired, and status there says so; global scope has no such gap.
- ADR 0003's consequence that wiring is files committed with the repository, and that Codex's server is registered per project, now describes the project scope only; the rest of ADR 0003 stands, but for Codex's global hook, which the amendment below replaces.
- Codex is wired like the other agents (amended 2026-10-26). The project scope writes the repository's `.codex/hooks.json` (the unmarked hook group) and `.codex/config.toml`, both committed; the global scope writes the marked group to `$CODEX_HOME/hooks.json` and `[mcp_servers.mdmem]` to `$CODEX_HOME/config.toml`. Neither scope writes the other's files. `enable codex` replaces 0.2.0's unmarked group in `$CODEX_HOME/hooks.json` with the marked one, and Codex asks for one more review. Codex reads a project's `.codex/` folders from the launch folder up to the work tree's root, so a global entry stays silent where any hooks file Codex reads for the session holds the project's entry for its part, not only the launch folder's as for Claude Code and Bob; in a linked worktree that file is the main checkout's. Codex runs a hook only once the user has reviewed it, keyed by the hooks file's path: we accept one review of the project hook per clone, which is Codex's own trust model, and a clone's worktrees share it. 0.2.0 kept one global hook to avoid a review per worktree, which Codex 0.164.0 does not ask for. `codex exec` never asks for the review, so a headless session in a clone nobody reviewed runs no project hook; in a repository wired in both scopes nothing speaks there until the review, as for Bob in an untrusted folder. Codex records each hook's review in its `config.toml`, which mdmem does not read yet.
- Each scope's wiring holds a third hook entry for every agent (amended 2026-10-29): a UserPromptSubmit group running `mdmem hook <agent> prompt`, in the same file as the agent's SessionStart group. In the global scope it carries `--global` and stays silent where the project's own prompt entry is present, by the rule each agent's session-start entries follow; in the project scope it is unmarked and committed with the rest. An agent counts as wired in a scope only with the prompt entry present, so a wiring made before it shows one missing entry until `mdmem enable` runs again, which adds only that entry, and `mdmem disable` removes it with the rest. Codex asks for one review of the new handler per hooks file, and `codex exec` never asks: the gap accepted above for the SessionStart group.
