# Two wiring scopes, global by default; the store is created on the first save

An agent is wired to mdmem in one of two scopes. In the global scope, the default of `mdmem enable`, the wiring lives in the agent's user-wide files and applies in every repository on the machine: the session-start hook speaks in every git repository, store or not, and the first memory write creates the store at the repository root. In the project scope (`mdmem enable --project`), the wiring lives in files committed with one repository, as 0.3.0's predecessor did for every project, and applies only there; enable creates the store if it is missing. A repository may be wired in both scopes, by different people: exactly one hook speaks, and the agent runs one mdmem server.

We chose this over keeping project files as the only wiring, which made every new repository need `mdmem init` and `mdmem enable` by hand before any agent remembered anything, and over global wiring alone, which would have left a team no way to wire a repository with a commit. A repository root is the only boundary the global hook trusts: outside git, `locateStore` walks up to the home directory for an existing store and would otherwise create one in the working directory, so a save in `~/dev` would make a store that every later `git init` under it stops seeing. Outside git the hook therefore speaks only where a store already exists, and only `mdmem init` creates one.

## Considered options

- Claude Code's own model, a store wherever a session runs: rejected for the walk-up trap above.
- A per-repository opt-out (a marker file, a variable): left out; a `.memory/` appears only on a save, and a global gitignore hides it everywhere at once.
- Importing Claude Code's memories inside `enable`, as before: impossible once enable runs once per machine. The import now runs when a store is created, by whichever path creates it, for a repository where Claude Code is wired in either scope and the per-repository marker is absent; a new store has nothing to conflict with, so `--prefer` is gone, and an existing store gets no import.

## Evidence

- All three agents spawn a user-scope stdio server in the session's working directory (the launch directory, or the `-C`/`-w` directory), never the home directory or `/`, so the server keeps resolving the store from `process.cwd()`, walking up to the repository (Claude Code 2.1.306, Codex 0.160.0, IBM Bob 2.0.6, tested 2026-10-21).
- Claude Code runs exactly one server named `mdmem` when the user scope and a project's `.mcp.json` both declare one: the user-scope one until the folder is trusted and the project server approved, then the project one. An approval written to `.claude/settings.local.json` has no effect in an untrusted folder (tested 2026-10-22). Both definitions run `mdmem mcp`, so which one wins does not matter.
- User-wide files: Claude Code's hooks, `permissions.allow` and `autoMemoryEnabled` in `~/.claude/settings.json` and its servers at the top-level `mcpServers` of `$CLAUDE_CONFIG_DIR/.claude.json`; Bob's `~/.bob/settings/settings.json` (hooks) and `~/.bob/settings/mcp.json` (what `bob mcp add -s global` writes); Codex's `~/.codex/hooks.json` and `[mcp_servers.*]` in `~/.codex/config.toml`. Codex's hooks are stable and on by default, with no feature flag to set.

## Consequences

- Global scope sets `autoMemoryEnabled: false` in Claude Code's user settings, so its auto memory is off on the whole machine; project scope sets it in the repository's `.claude/settings.json` only. A project's `true` overrides a user's `false`, and the check keeps reporting it.
- The global hook entries carry a marker (`mdmem hook <agent> <part> --global`); the project entries stay as 0.2.0 wrote them, so a 0.2.0 repository is a project-scoped one with no migration. A global instance stays silent where the project's own hook entries are present (the server registration alone does not count). Codex keeps one unmarked hook in `~/.codex/hooks.json` in both scopes, since Codex binds a hook's approval to its file's path; it speaks where the mdmem server is registered in the user config or the project's `.codex/config.toml`. Whether Codex passes `CODEX_HOME` to hooks is unverified; the hook reads `~/.codex` when the variable is absent.
- In a repository with no store, the index part says the store does not exist yet and that the first `memory_write` creates it. Any memory write creates it (MCP `memory_write`, CLI `mdmem add`), with `MEMORY.md`; reads refuse until then and say so. The creating write reports the store's path, the import's lines when it imported, and the existing note when git does not ignore `.memory/`.
- `mdmem status` reports each agent in both scopes and works without a store and outside any repository; the check reports the wiring alone there. A repository wired in both scopes is two status lines, not a problem. `mdmem disable` mirrors enable: global by default, `--project` for the repository's files; `--global` is gone.
- In an untrusted folder wired in both scopes for Claude Code, nothing speaks until the folder is trusted: project hooks do not run before trust, and the global hook defers to the project entries it can see. Same as 0.2.0.
- Worktrees are unchanged from ADR 0003: the store is keyed by the repository, so every worktree shares it. In project scope the wiring files travel with the commit, so a worktree checked out before that commit is not wired, and status there says so; global scope has no such gap.
- ADR 0003's consequence that wiring is files committed with the repository, and that Codex's server is registered per project, now describes the project scope only; the rest of ADR 0003 stands.
